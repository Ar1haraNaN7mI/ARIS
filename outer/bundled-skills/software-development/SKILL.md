# 仓库中的代码修改

1. 从用户遇到的行为出发，确认入口、输入和期望结果。查看工作树状态，用 `project_checks` 找到该文件所属包的贡献说明、构建和测试入口。阅读离修改点最近的约定、调用方和已有测试。
2. 修复缺陷时先复现。记录能暴露问题的最小输入、失败断言或退出码。遇到依赖缺失、权限或配置问题时，先定位是哪一步没有启动。新增功能可先用一个例子约定外部行为。
3. 沿调用路径修改实际实现，保留其他人的改动。用 `grep` 查调用方和相似实现，读取局部上下文后再编辑。测试应断言使用者可观察的结果，涵盖触发缺陷的边界。变更跨包时，约定每个文件的负责人和集成顺序。
4. 在对应包的目录实际运行检查。用户点名验收命令时，在最后一次相关编辑后单独原样运行。失败时从首个相关诊断定位原因，修正并重跑。按影响范围决定是否补跑相邻调用方或完整测试集。
5. 检查最终 diff 和工作树，交付修改的行为、具体验证命令和结果。判断来自测试日志还是人工检查要写清楚。保留仍会影响使用的限制和复现条件。
